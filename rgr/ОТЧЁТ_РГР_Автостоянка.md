## 1. Описание предметной области и бизнес-правил

Автостоянка оказывает услуги платного хранения транспортных средств (ТС).
Учёт ведётся на основании трёх исходных документов.

| Документ | Данные, которые он даёт модели |
|---|---|
| Договор с клиентом | клиент, ТС, машино-место, тариф, срок действия договора, оформивший сотрудник, сумма |
| Квитанция об оплате услуги автостоянки | номер квитанции, дата, сумма, способ оплаты, принявший платёж кассир; по одному договору квитанций может быть **несколько** — допускается частичная оплата |
| Электронная регистрация на въезде по госномеру | время проезда, направление (въезд/выезд), строка государственного номера, распознанная камерой, достоверность распознавания, номер ворот |

### Бизнес-правила предметной области

1. Клиент (физическое или юридическое лицо) может заключить множество
   договоров. Анонимные договоры не заключаются.
2. Клиенту может принадлежать несколько ТС; каждое ТС принадлежит ровно
   одному клиенту.
3. Государственный регистрационный знак (ГРЗ) уникален в пределах базы
   данных — именно по нему работает электронная регистрация на въезде.
4. Каждое ТС относится ровно к одной категории (легковой, внедорожник,
   грузовой, мотоцикл); в категории может быть множество ТС.
5. Машино-место имеет уникальный адрес «сектор + номер» и рассчитано на
   определённую категорию ТС.
6. Договор связывает одного клиента, одно ТС, одно машино-место и один
   тариф; оформляется одним сотрудником.
7. Одно машино-место не может быть занято двумя действующими договорами
   с пересекающимися сроками. Одно ТС не может одновременно храниться по
   двум действующим договорам.
8. Оплата договора допускается частями: договору соответствует множество
   квитанций, каждая квитанция относится ровно к одному договору. Сумма
   платежа строго положительна.
9. Событие проезда фиксируется автоматически. Если номер не распознан или
   ТС не зарегистрировано в базе, событие всё равно сохраняется — с «сырой»
   строкой номера и без ссылок на ТС и договор.
10. Сотрудники находятся в отношении подчинённости (администратор —
    кассиры и охранники): между экземплярами сущности СОТРУДНИК действует
    рекурсивная связь.
11. Удаление сотрудника не должно уничтожать оформленные им договоры и
    принятые квитанции: это финансовые документы.

## 2. Логическая модель данных

На основании анализа предметной области выделены девять сущностей:
**КЛИЕНТ, СОТРУДНИК, КАТЕГОРИЯ ТС, ТРАНСПОРТНОЕ СРЕДСТВО, МАШИНО-МЕСТО,
ТАРИФ, ДОГОВОР, КВИТАНЦИЯ, ПРОЕЗД.**

Между сущностями установлены неидентифицирующие связи мощностью
«один-ко-многим». Между экземплярами сущности СОТРУДНИК установлена
рекурсивная связь, отражающая подчинённость сотрудников.

| Родительская сущность | Дочерняя сущность | Мощность | Смысл связи |
|---|---|---|---|
| КЛИЕНТ | ТРАНСПОРТНОЕ СРЕДСТВО | 1:М | клиенту принадлежит несколько ТС |
| КЛИЕНТ | ДОГОВОР | 1:М | клиент заключает несколько договоров |
| КАТЕГОРИЯ ТС | ТРАНСПОРТНОЕ СРЕДСТВО | 1:М | в категории несколько ТС |
| КАТЕГОРИЯ ТС | МАШИНО-МЕСТО | 1:М | место рассчитано на категорию ТС |
| КАТЕГОРИЯ ТС | ТАРИФ | 1:М | тариф установлен для категории ТС |
| ТРАНСПОРТНОЕ СРЕДСТВО | ДОГОВОР | 1:М | на одно ТС могут заключаться договоры в разное время |
| МАШИНО-МЕСТО | ДОГОВОР | 1:М | место сдаётся по договорам в разное время |
| ТАРИФ | ДОГОВОР | 1:М | по тарифу заключается множество договоров |
| СОТРУДНИК | ДОГОВОР | 1:М | сотрудник оформляет множество договоров |
| СОТРУДНИК | КВИТАНЦИЯ | 1:М | кассир принимает множество платежей |
| СОТРУДНИК | СОТРУДНИК | 1:М | рекурсивная связь «руководитель — подчинённый» |
| ДОГОВОР | КВИТАНЦИЯ | 1:М | договор оплачивается частями |
| ТРАНСПОРТНОЕ СРЕДСТВО | ПРОЕЗД | 1:М | по одному ТС фиксируется множество проездов |
| ДОГОВОР | ПРОЕЗД | 1:М | проезды относятся к действующему договору |
| МАШИНО-МЕСТО | ПРОЕЗД | 1:М | проезд связан с занимаемым местом |

## 4. Обеспечение целостности данных

### 4.1. Целостность по сущностям

Целостность по сущностям требует, чтобы каждая строка таблицы была
однозначно идентифицируема, а первичный ключ не содержал неопределённых
значений. В разработанной базе данных каждая таблица имеет первичный ключ —
суррогатный числовой атрибут `*_ID` с ограничением `PRIMARY KEY`, которое
автоматически сочетает в себе `UNIQUE` и `NOT NULL` и создаёт уникальный
индекс В-дерева.

Суррогатный ключ выбран потому, что естественный ключ транспортного
средства — государственный регистрационный знак — может измениться при
перерегистрации автомобиля, а на ТС ссылаются договоры и записи журнала
проездов. Естественные (потенциальные) ключи объявлены отдельными
ограничениями `UNIQUE`:

| Таблица | Первичный ключ | Потенциальные ключи (UNIQUE) |
|---|---|---|
| vehicle_categories | cat_ID | cat_name |
| clients | cl_ID | cl_doc |
| employees | emp_ID | — |
| vehicles | veh_ID | veh_plate |
| places | pl_ID | (pl_sector, pl_number) |
| tariffs | tar_ID | (tar_name, tar_cat_ID, tar_date_from) |
| contracts | contr_ID | contr_number |
| payments | pay_ID | pay_receipt_no |
| passages | pass_ID | (pass_plate_raw, pass_time, pass_direction) |

Составное ограничение уникальности таблицы `passages` отражает физический
смысл: камера не может дважды зафиксировать один и тот же номер в одном
направлении в один и тот же момент времени.

### 4.2. Семантическая целостность

Семантическая (доменная) целостность обеспечивает соответствие значений
атрибутов смыслу предметной области. Она реализована выбором типов данных,
ограничениями `NOT NULL`, значениями `DEFAULT` и девятнадцатью ограничениями
проверки `CHECK`.

| Ограничение | Таблица | Смысл ограничения |
|---|---|---|
| clients_CK_type | clients | тип клиента ∈ {'Ф', 'Ю'} |
| clients_CK_discount | clients | скидка находится в диапазоне 0…30 % |
| employees_CK_chief | employees | сотрудник не может быть руководителем самого себя |
| categories_CK_coef | vehicle_categories | тарифный коэффициент строго положителен |
| vehicles_CK_plate | vehicles | длина ГРЗ составляет 8 или 9 символов |
| places_CK_status | places | статус места ∈ {'свободно', 'занято', 'ремонт'} |
| places_CK_level | places | уровень стоянки в диапазоне −2…10 |
| places_CK_number | places | номер места положителен |
| tariffs_CK_price | tariffs | цена тарифа строго положительна |
| tariffs_CK_period | tariffs | период ∈ {'час', 'сутки', 'месяц'} |
| tariffs_CK_dates | tariffs | дата отмены тарифа не раньше даты ввода |
| contracts_CK_dates | contracts | дата окончания договора не раньше даты начала |
| contracts_CK_signed | contracts | договор не может быть подписан позже начала срока хранения |
| contracts_CK_amount | contracts | сумма договора неотрицательна |
| contracts_CK_status | contracts | статус ∈ {'оформлен', 'действующий', 'завершён', 'расторгнут'} |
| payments_CK_sum | payments | сумма квитанции строго положительна |
| payments_CK_method | payments | способ оплаты ∈ {'наличные', 'карта', 'перевод'} |
| passages_CK_dir | passages | направление проезда ∈ {'IN', 'OUT'} |
| passages_CK_conf | passages | достоверность распознавания в диапазоне 0…1 |

Проверка государственного номера ограничивает его длину: восемь символов
в обычном формате (`А123ВС55`) или девять при трёхзначном коде региона
(`С369МН155`):

```sql
ALTER TABLE vehicles
ADD CONSTRAINT vehicles_CK_plate CHECK (length(veh_plate) BETWEEN 8 AND 9);
```

Ограничение `contracts_CK_dates` допускает значение NULL в столбце
`contr_end`, что соответствует бессрочному договору, и одновременно
запрещает указывать дату окончания раньше даты начала:

```sql
ALTER TABLE contracts
ADD CONSTRAINT contracts_CK_dates
CHECK (contr_end IS NULL OR contr_end >= contr_start);
```

### 4.3. Ссылочная целостность

Ссылочная целостность поддерживается пятнадцатью ограничениями
`FOREIGN KEY`. Для всех связей установлено правило `ON UPDATE CASCADE`:
изменение первичного ключа родительской строки автоматически
распространяется на дочерние строки.

Правило `ON DELETE CASCADE` задано для двенадцати связей: удаление
родительской строки удаляет зависящие от неё строки дочерней таблицы.
Например, удаление клиента влечёт удаление принадлежащих ему
транспортных средств, заключённых с ним договоров и, по цепочке,
квитанций по этим договорам.

Для трёх связей задано правило `ON DELETE SET NULL`. Оно применено там,
где столбец внешнего ключа допускает значение NULL и где дочерняя строка
должна сохраняться после удаления родительской.

| Внешний ключ | Дочерняя таблица | Родительская таблица | ON DELETE | Обоснование выбора правила |
|---|---|---|---|---|
| employees_FK | employees | employees | SET NULL | рекурсивная связь; увольнение руководителя не должно удалять его подчинённых |
| vehicles_FK1 | vehicles | clients | CASCADE | карточка ТС существует в базе только как имущество клиента |
| vehicles_FK2 | vehicles | vehicle_categories | CASCADE | ТС не может существовать вне категории |
| places_FK | places | vehicle_categories | CASCADE | то же для машино-мест |
| tariffs_FK | tariffs | vehicle_categories | CASCADE | то же для тарифов |
| contracts_FK1 | contracts | clients | CASCADE | договор не существует без заказчика |
| contracts_FK2 | contracts | vehicles | CASCADE | договор оформлен на конкретное ТС |
| contracts_FK3 | contracts | places | CASCADE | договор заключён на конкретное машино-место |
| contracts_FK4 | contracts | tariffs | CASCADE | договор рассчитан по конкретному тарифу |
| contracts_FK5 | contracts | employees | CASCADE | договор оформлен конкретным сотрудником |
| payments_FK1 | payments | contracts | CASCADE | квитанции — неотъемлемая часть договора |
| payments_FK2 | payments | employees | CASCADE | квитанция выписана конкретным кассиром |
| passages_FK1 | passages | vehicles | SET NULL | факт проезда зафиксирован камерой и остаётся в журнале |
| passages_FK2 | passages | contracts | SET NULL | то же |
| passages_FK3 | passages | places | SET NULL | то же |

Столбцы внешних ключей объявлены `NOT NULL` везде, где связь обязательна:
это гарантирует, что ограничение внешнего ключа соблюдается всегда.
Значение NULL допускается только для `emp_chief_ID` (у руководителя
организации нет начальника) и для трёх внешних ключей таблицы `passages`,
которые фиксируют проезд незарегистрированного автомобиля.

Бизнес-правило 7 (одно машино-место не может быть занято двумя
действующими договорами с пересекающимися сроками) ограничениями
`UNIQUE`, `CHECK` и `FOREIGN KEY` невыразимо, поскольку требует сравнения
не отдельных значений, а интервалов дат. В рамках настоящей работы
контроль этого правила возлагается на приложение; средствами СУБД его
можно реализовать триггером, срабатывающим при вставке и изменении строк
таблицы `contracts` (лабораторная работа № 11).

определение ограничений облегчает их модификацию и удаление.

### 5.1. Создание базы данных

```sql
CREATE DATABASE parking
    WITH
    OWNER            = postgres
    ENCODING         = 'UTF8'
    LC_COLLATE       = 'Russian_Russia.1251'
    LC_CTYPE         = 'Russian_Russia.1251'
    TEMPLATE         = template0
    TABLESPACE       = pg_default
    CONNECTION LIMIT = -1
    IS_TEMPLATE      = False;

COMMENT ON DATABASE parking
    IS 'База данных автостоянки: договоры с клиентами, транспортные средства,
        электронная регистрация проездов по госномеру, оплата услуг';
```

Создаётся база данных `parking` со следующими характеристиками:
владелец — суперпользователь `postgres`; кодировка UTF-8; порядок сортировки
строк и классификация символов определяются локалью `Russian_Russia.1251`;
табличное пространство — `pg_default`; ограничение на количество
одновременных подключений отсутствует; клонировать базу могут только
суперпользователи и её владелец. Указание `TEMPLATE = template0`
необходимо потому, что задаваемая локаль может отличаться от локали
шаблонной базы `template1`.

### 5.3. Ограничения целостности по сущностям и семантической целостности

```sql
ALTER TABLE vehicles ADD CONSTRAINT vehicles_UK UNIQUE (veh_plate);
ALTER TABLE places   ADD CONSTRAINT places_UK   UNIQUE (pl_sector, pl_number);
ALTER TABLE payments ADD CONSTRAINT payments_UK UNIQUE (pay_receipt_no);

ALTER TABLE places    ALTER COLUMN pl_status    SET DEFAULT 'свободно';
ALTER TABLE contracts ALTER COLUMN contr_status SET DEFAULT 'оформлен';
ALTER TABLE payments  ALTER COLUMN pay_date     SET DEFAULT now();

ALTER TABLE vehicles ADD CONSTRAINT vehicles_CK_plate
CHECK (length(veh_plate) BETWEEN 8 AND 9);

ALTER TABLE contracts ADD CONSTRAINT contracts_CK_dates
CHECK (contr_end IS NULL OR contr_end >= contr_start);

ALTER TABLE payments ADD CONSTRAINT payments_CK_sum CHECK (pay_sum > 0);
```

-- Рекурсивная связь «руководитель — подчинённый»

ON UPDATE CASCADE;

ON UPDATE CASCADE;

ALTER TABLE payments

ON DELETE CASCADE
ON UPDATE CASCADE;

## 8. Выводы

В ходе выполнения расчётно-графической работы средствами СУБД PostgreSQL
спроектирована и реализована база данных `parking` для предметной области
«Автостоянка». База данных состоит из девяти таблиц и полностью покрывает
три исходных документа предметной области: договор с клиентом, квитанцию
об оплате услуги автостоянки и электронную регистрацию на въезде по
государственному номеру автомобиля.

Целостность данных обеспечена на трёх уровнях.

1. **Целостность по сущностям** — девятью первичными ключами и восемью
   ограничениями уникальности естественных ключей, среди которых
   государственный номер ТС, номер договора, номер квитанции и адрес
   машино-места «сектор + номер».
2. **Семантическая целостность** — выбором типов данных, ограничениями
   `NOT NULL`, значениями по умолчанию и девятнадцатью ограничениями
   `CHECK`, которые контролируют допустимые перечни значений (тип клиента,
   статус договора, способ оплаты, направление проезда), числовые
   диапазоны (скидка, достоверность распознавания, уровень стоянки) и
   согласованность дат договора.
3. **Ссылочная целостность** — пятнадцатью внешними ключами. Для всех
   связей задано правило `ON UPDATE CASCADE`; для двенадцати связей —
   `ON DELETE CASCADE`, обеспечивающее каскадное удаление зависимых
   строк, и для трёх связей с необязательными внешними ключами —
   `ON DELETE SET NULL`, благодаря которому журнал проездов сохраняется
   при удалении сведений о транспортном средстве или договоре.

Всего в базе данных создано 51 ограничение целостности, не считая
ограничений `NOT NULL`.

Работоспособность всех ограничений подтверждена двенадцатью контрольными
проверками, каждая из которых была отвергнута сервером с соответствующим
сообщением об ошибке, а также двумя проверками каскадного удаления,
выполненными в транзакциях с откатом.

Дальнейшее развитие базы данных предполагает создание представлений для
отчётности, хранимых процедур для операций ввода и корректировки данных,
а также триггеров для автоматического изменения статуса машино-места при
въезде и выезде транспортного средства.
